# Solar Launcher V0.4 — Patch Engine

Solar V0.4 adds the first code/gameplay patching layer to the framework.

## Goals

- Load declarative memory patches from enabled Solar mods.
- Verify expected bytes before changing memory.
- Refuse invalid/unmapped/read-only memory ranges instead of blindly writing.
- Resolve overlapping memory patches using Solar mod priority.
- Restore all applied memory patches when the application ends.
- Initialize `FunctionPatcherModule` support for native hooks.
- Allow future Solar Game Adapters to register named native hooks.

## Folder layout

```text
MyMod/
├── mod.json
├── content/
├── aoc/
└── patches/
    └── gameplay.json
```

A mod can be patch-only; `content/` and `aoc/` are optional.

## Patch file format

```json
{
  "formatVersion": 1,
  "titleId": "00050000XXXXXXXX",
  "enabled": true,
  "patches": [
    {
      "name": "Example player count",
      "address": "0x12345678",
      "expected": "00 00 00 02",
      "replace": "00 00 00 03",
      "executable": false
    }
  ],
  "hooks": [
    "example.game.createPlayer3"
  ]
}
```

### Memory patch fields

- `name` — human-readable patch name.
- `address` — Wii U effective virtual address written as a string, usually hexadecimal.
- `expected` — bytes Solar must find before applying the patch.
- `replace` — replacement bytes. Must have exactly the same length as `expected`.
- `executable` — optional. If `true`, Solar also invalidates the instruction cache after writing/restoring.
- `enabled` — optional per-patch toggle. Defaults to `true`.

V0.4 limits one memory patch to 512 bytes and one patch file to 128 patch entries.

## Safety model

Solar V0.4 does **not** blindly write arbitrary addresses.

Before applying a memory patch it checks:

1. The mod itself is enabled.
2. The patch file Title ID matches the running game when specified.
3. The address range is valid and mapped as read/write.
4. `expected` and `replace` have the same non-zero length.
5. The bytes currently in memory exactly match `expected`.
6. No higher-priority Solar memory patch already owns an overlapping range.

If any check fails, the patch is skipped and written to the Solar log.

Higher Solar priority wins for overlapping memory patches.

All successful memory patches are backed up and restored in reverse order when the application ends.

## Native hooks

Complex gameplay modifications often require function hooks rather than raw values.

Solar V0.4 initializes `libfunctionpatcher` and introduces `NativeHookRegistry`.

A patch file may request a hook by ID:

```json
{
  "hooks": ["cuphead.playerManager.createPlayer3"]
}
```

The hook will only run if a compiled Solar Game Adapter registered that exact ID. Solar will **not execute arbitrary machine code or plugins supplied inside a mod folder**.

This keeps SD mod packages declarative while game-specific native code remains part of a reviewed/compiled Solar adapter.

Function hooks are removed when the application ends.

## Cuphead 3 Player

The planned Cuphead 3-player test mod will use this V0.4 foundation after the Wii U RPX has been extracted and analyzed.

Likely responsibilities will be split between:

- memory patches for safe constants/state where appropriate;
- native hooks for player creation, input, camera, HUD, revives, targeting and map/game-state integration;
- file redirection for Player 3 sprites and UI assets.

No Cuphead-specific addresses or hooks are included in V0.4 yet.
